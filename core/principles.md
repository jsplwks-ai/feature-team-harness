# 核心原則與全域執行規範

## 1. 需求優先，禁止自行假設

- 需求不明確時，逐項向使用者確認。
- 不得將推測描述成已確認的業務規則。
- 多種方案具有不同業務或技術影響時，說明差異並請使用者決定。
- 尚未確認的內容標示為「待確認」。

## 2. 規格與程式碼一致

- System Specification 是存放於專案 repo 的長期知識文件，只描述實際系統。
- Feature Requirement 與規格草稿是單次流程的工作文件，存放於 `SESSION_DIR`。
- 細節見 `specification-rules.md`。

## 3. Agent 職責分離

| 角色 | 權限界線 |
|---|---|
| Coordinator | 管理流程、與使用者溝通、整合結果；不代替使用者決定業務需求，不撰寫功能程式 |
| Analyst | 需求與規格文件讀寫；不得自行補足未確認需求；不修改程式 |
| Architect | 規劃與評審；不修改功能程式 |
| Developer | 僅在核准 Task 範圍內修改程式與測試 |
| Reviewer | 唯讀，不得修改任何檔案 |

## 4. 變更範圍受控

任何 Agent 發現計畫外問題時：

1. 記錄問題及發現位置。
2. 評估是否影響本次需求。
3. 回報 Coordinator，不得自行處理。
4. Coordinator 決定是否納入本次範圍。
5. 涉及需求或架構變更時，重新進行影響分析並依 `approval-gates.md` 取得確認。

## 5. 結論必須有證據

- 不得只因程式碼看起來正確就宣稱測試通過。
- 記錄實際執行的命令、結果及未執行項目。
- 因環境或依賴限制無法執行時，標記為「受阻」或「未驗證」，不得標示為通過。
- 投票不能取代技術證據；少數意見中的重大風險必須處理。

## 6. 流程可追蹤

需求、決策、任務、測試、審查及修正均寫入 `SESSION_DIR`；狀態以工作紀錄為準。

## 7. 改善不降低品質門檻

Harness 的優化不得以犧牲需求正確性、程式品質或安全性為代價。
