# 交叉審核與投票規則

## 共通原則

- 投票必須記錄立場（支持／反對／保留）及理由與證據。
- 2:1 不代表爭議自動解決。
- 涉及需求解讀、資料安全、重大相容性或高風險設計的分歧，必須取得足夠證據；無法解決時交由使用者決策。
- 不得為了取得一致而刪除少數意見；少數意見須保留於評審紀錄。

## 架構評審（Phase 4）

1. 第一輪：評審者 A／B／C 各自閱讀需求、規格草稿、相關程式碼及初版實作計畫，獨立產出分析及方案（`plan/architect-{A,B,C}.md`）。
2. 第二輪：Coordinator 轉達另外兩份方案。每位評審者針對**每一份方案**（含自己的）投票：支持／反對／保留，並附理由與證據；同時提出對他方設計缺陷、遺漏、複雜度、風險的檢查意見。
3. 計票：以「支持」票數最多的方案為採用方案。
4. 整合：由採用方案的提出者以 `SendMessage` 整合成最終實作計畫，須納入評審發現的缺漏，並保留未採用方案及原因。
5. 平票：Coordinator 整理各方案差異及取捨，交由使用者選定方案，再由該方案提出者整合。

## 程式碼審查（Phase 6）

1. 第一輪：Reviewer A／B／C 各自獨立產出問題清單及審查結論。
2. 第二輪：Coordinator 轉達另外兩份結果。每位 Reviewer 檢查漏報、誤判及缺乏證據的問題，並對**非三方共同提出**的問題投票：是否成立、嚴重程度是否正確。
3. Coordinator 整合：
   - 三方皆支持：成立。
   - 有分歧：依證據判斷；Critical／Major 只要有一方支持且未被證據排除，即不得以多數決駁回，須要求補充證據或交由使用者決策。
   - 缺乏證據的問題：要求提出者補證；無法補證則不採用並記錄原因。

## 評審紀錄格式

每個評審項目至少記錄：

| 欄位 | 說明 |
|---|---|
| Agent | Agent 識別名稱 |
| 提案／發現 | 方案或問題內容 |
| 證據 | 文件、程式碼位置、測試結果或技術依據 |
| 交叉審核意見 | 其他 Agent 的支持、反對或補充 |
| 投票 | 支持、反對、保留 |
| 理由 | 判斷依據 |
| 最終決議 | 採用、修改、不採用或待使用者決定 |
