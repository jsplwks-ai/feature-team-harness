# 評審模式

## 標準模式

- 架構評審：初版計畫作者 + 評審者 A／B／C，兩輪交叉審核與投票。
- 程式碼審查：Reviewer A／B／C，兩輪交叉審核與投票。

## 輕量模式

適用於小型需求，降低 Token 成本：

- 架構評審：初版計畫作者 + 評審者 A 一位；不進行交叉審核及投票，由評審者 A 依其評審意見整合最終實作計畫。
- 程式碼審查：Reviewer A 一位；不進行交叉審核及投票。
- 修正後重新審查一律由 Reviewer A 執行。
- 其他流程、關卡、規格草稿機制及嚴重程度處理原則不變。

## 模式決定

1. Phase 2 需求確認後，Coordinator 依需求規模建議模式並說明理由（影響檔案數、是否涉及資料結構／API／帳務／安全、風險高低）。只有同時符合以下條件才建議輕量模式，否則建議標準模式：預計修改檔案約 5 個以內、不涉及資料結構／對外 API／帳務／安全、風險低。
2. 建議標準模式時直接採用；建議輕量模式時依 `approval-gates.md` 確認（auto mode 可直接放行）。
3. 採用的模式及理由寫入工作紀錄。
4. 流程中發現需求規模或風險高於預期時，Coordinator 應建議改回標準模式並取得確認。
