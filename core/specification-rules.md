# 規格規則

## 文件類型

| 文件類型 | 定位 | 存放位置 |
|---|---|---|
| Feature Requirement | 單次需求的背景、目標、確認內容及驗收條件 | `SESSION_DIR/requirement.md` |
| 規格草稿 | 本次需求預計對 System Specification 的新增或修改 | `SESSION_DIR/spec-draft.md` |
| System Specification | 長期業務規則、系統架構、資料模型、API 及功能規格 | 專案 repo |

## 規格路徑

- 由專案 `CLAUDE.md` 寫明 System Specification（或知識集）的位置。
- 找不到時由 Coordinator 詢問使用者，並將答案寫入工作紀錄。
- 專案尚無規格文件時，詢問使用者是否建立及存放位置，不得自行決定。

## 草稿階段（Phase 3–5）

- Phase 3 只產生規格草稿，不修改專案 repo 內的 System Specification。
- 依專案既有文件結構分類（系統架構、功能模組、業務規則、資料模型、API、服務互動、權限、系統限制等）。
- 修改既有功能時，檢查對應規格是否需要更新並列入草稿；新增功能時，於草稿新增對應規格。
- 架構規劃或實作過程中設計有變動時，同步更新草稿。
- 發現既有規格與程式碼不一致時，記錄於草稿的「既有不一致」區，交由使用者決定是否處理。

## 正式寫入（Step 6.8）

- 審查通過後，Analyst 依**實際程式行為**將草稿寫入專案 repo 的 System Specification。
- 寫入內容不得超出已實作範圍。
- 發現實作與已確認需求不一致時，先回報 Coordinator 處理差異，不得反向修改需求文件掩蓋問題。

## 變更紀錄

草稿的「變更紀錄」區記錄：新增或修改的規格文件、變更原因、影響模組、對應需求 ID、實作狀態（草稿／已實作／已寫入）。
